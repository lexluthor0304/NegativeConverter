# Desktop in-app updates

The direct-download desktop builds (Windows NSIS/MSI, Linux AppImage/deb/rpm,
macOS DMG) update themselves through `tauri-plugin-updater`. Every merge to
`main` that goes through `.github/workflows/desktop-release.yml` signs the
installers, uploads them to R2 and refreshes
`negative-converter/release/updater.json`; installed apps pick the new version
up from there. Nobody has to re-download anything by hand.

The Mac App Store build is excluded: App Store apps must not replace
themselves, so `scripts/build-mas.sh` compiles with `--no-default-features`
(drops the `updater` cargo feature) and `build.rs` then leaves the `updater`
capability out of the ACL.

## Flow inside the app

1. Once a day `main.js` fetches `latest.json` (unchanged) and shows the update
   banner when it lists a newer version.
2. On start the webview asks the backend `get_desktop_update_capability`. When
   the build can replace itself the banner button reads "Download and
   install"; otherwise (App Store build, unpackaged binary, a previous in-app
   failure) it opens the download page as before.
3. "Download and install" calls `updater.check()`, then
   `downloadAndInstall()` with progress in the banner, then relaunches. On
   Windows the plugin hands over to the installer (`installMode: passive`) and
   exits by itself. deb/rpm installs go through `pkexec`, so a password prompt
   appears. If `updater.json` has no signed entry for the running build, or
   the download fails, the app falls back to the download page.

## Manifest keys

`.github/scripts/r2_sync_release.py` derives `updater.json` from the release
assets that have a `.sig` next to them (`scripts/check-updater-manifest.mjs`
covers it):

| Key | Asset |
| --- | --- |
| `windows-x86_64-nsis`, `windows-x86_64` | `*_x64-setup.exe` |
| `windows-x86_64-msi` | `*_x64_en-US.msi` |
| `linux-x86_64-appimage`, `linux-x86_64` | `*_amd64.AppImage` |
| `linux-x86_64-deb` / `linux-x86_64-rpm` | `.deb` / `.rpm` (only when the bundler signed them) |
| `linux-x86_64-glibc235` | `*_legacy-glibc235.AppImage` |
| `darwin-aarch64-app`, `darwin-aarch64` | `*_aarch64.app.tar.gz` |

The plugin looks up `<os>-<arch>-<installer>` first and `<os>-<arch>` second.
The legacy AppImage is compiled with `NC_UPDATER_TARGET=linux-x86_64-glibc235`
(read by `option_env!` in `src-tauri/src/lib.rs`), so it looks up exactly that
key and never replaces itself with the standard AppImage, which would not
start on the older distributions it exists for.

## Signing

Installers are signed with a minisign key pair generated by
`tauri signer generate`. The public key lives in `src-tauri/tauri.conf.json`
(`plugins.updater.pubkey`); the app refuses any download whose signature does
not match it.

| Secret | Content |
| --- | --- |
| `TAURI_SIGNING_PRIVATE_KEY` | contents of the private key file |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | its password |

The release workflow fails early when the private key secret is missing, and
the R2 step refuses to publish an `updater.json` without platforms. Only the
release workflow passes `--config src-tauri/tauri.release.conf.json`
(`createUpdaterArtifacts`), so pull-request and local builds need no key.

Keep an offline backup of the private key: a new key pair would leave every
installed copy unable to verify further updates, and users would have to
download the app once more by hand. Rotating it deliberately means shipping
one release that still carries the old public key, then switching.

## Local check

Build twice with a test manifest served from localhost, install the older
build somewhere writable, click the banner button, and confirm the bundle's
version afterwards:

```bash
# the CLI reads the key contents (TAURI_SIGNING_PRIVATE_KEY_PATH is not enough)
export TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/negative-converter.key)"
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD="$(cat ~/.tauri/negative-converter.key.password)"
# override version + endpoint via --config (dangerousInsecureTransportProtocol for http://127.0.0.1)
npm run tauri:build -- --bundles app --config src-tauri/tauri.release.conf.json --config /tmp/updater-test.json
```

Give the test builds their own `identifier` in that override: the daily check
is skipped for 24 h once `nc_desktop_update_last_check_ts` is in the app's
WebKit storage, and a separate identifier keeps the real app's data untouched.
`r2_sync_release.py --dry-run --source-dir <dir> --manifest-dir <serve dir>`
writes the test `updater.json` (the dir needs at least one installer file).
Verified on macOS on 2026-09-09: 0.0.1 → banner → button → 0.0.2 relaunched.
