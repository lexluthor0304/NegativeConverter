# 調色プレビューの連続更新

## 原因と変更

従来は変換用プレビューを最大 25 万画素へ縮小し、原寸処理の完了後も、
次の調整でこの小画像を表示用テクスチャへ戻していた。
さらに主要な SilverCore スライダーの `input` は再変換を行わず、
`change` 後の 80ms デバウンスで初めて正しい色調を反映していた。

- 表示領域・DPR・ズーム倍率から表示用画像を作成。整数間引きをやめ、16bit 値を保持して補間する。
- 解析標本は従来の独立した 16bit 標本を維持。表示解像度によって成像領域の定義を変えない。
- プレビュー専用 Worker を追加。原寸変換・書き出しのキューとは独立させる。
- Worker 内では一枚分の入力と解析参照だけを再利用。JPEG 等の 8bit 入力も初回のみ 16bit 化する。
- スライダーの `input` で変換を要求し、16ms の間隔で最新要求をまとめる。処理中は直近一件だけを保持する。（#233 でフレーム単位の送信に置き換え。末尾の節を参照）
- 連続入力中も完成したフレームを描画する。別の画像・無効化された履歴・古い原寸結果は採用しない。
- CPU プレビューと WebGL の表示元を同じ解像度にする。直方図の標本も調色に追従させる。
- ウィンドウ変更・ズーム・DPR 変更後の操作でプレビューを更新する。

画面表示用画像は最大 400 万画素かつ GPU のテクスチャ上限以内。
（#248 以降、表示用画像はズームに従わず、拡大時の原寸の画素は詳細レイヤーが
表示する。末尾の節を参照。）
全解像度の画像と 16bit 書き出し経路は別途保持する。

## 検証

`displayPreview.test.mjs` は DPR・縦横・ズーム・容量上限・16bit 補間・入力不変を検証する。
`conversionWorkerClient.test.mjs` は入力再利用・参照解除・再起動・独立キュー・部分配列を検証する。
`conversionWorker.test.mjs` は実ルーターでカラー・白黒・正像を変換し、
転送後の再利用と参照切替を含め、同じ入力の主スレッド変換と 16bit 出力が完全一致することを確認する。

Chrome smoke に `realtime-preview-smoke.mjs` を追加。
実画像を読み込み、DPR 1 / 2 で `input` を約 16ms ごとに 60 回発火させ、
`change` 前のテクスチャ画素の変化、実描画回数、表示解像度維持、最新入力への収束、
Worker 入力の再利用を検証する。フレームレートの保証や全端末のベンチマークではない。
フレームレートと input→draw の計測は `npm run bench:interactive` の S2/S3（信頼された入力、
60 Hz、本番ビルド）で行う（`docs/performance-benchmark.md`）。

失敗ファイルへの切替テストは、指紋を採る前に原寸の画布が揃うまで待つ。
通常の非同期原寸化をファイル切替による画像破損と誤認しないための変更であり、
切替失敗後の画像・選択位置の厳密比較は維持する。

今回の実行結果: `npm test` 48/48、全 Chrome smoke、Web build が成功。
実ファイル `DSC_8800.NEF` の操作テストも成功。
DPR 1 は 916×611 の画素を維持して約 1.03 秒の入力中に 50 回更新し、初回描画は約 38ms。
DPR 2 は 1832×1222 を維持して約 1.18 秒の入力中に 13 回更新した。
後者の初回約 256ms には DPR 切替に伴うプレビュー再生成も含む。
同じ速度・60fps を全環境で保証する数値ではない。
2 倍表示は 786×524 から 1572×1048 へ増え、調色中も同じ解像度を維持した。
WebGL を無効にした CPU 表示でも `change` 前に画素が変化することを確認した。

```sh
npm test
npm run test:smoke
npm run build:web
# ローカル実 RAW がある場合のみ（ファイルを変更・送信しない）
node output/playwright/realtime-nef.mjs
```

## 残る制約

除塵・修復が有効な場合も、操作中はプレビューだけを変換する（#237、末尾の節）。
原寸の変換・検出・修復は入力が止まった後に一度だけ行うため、操作中の表示には
塵が残り、修復済みの画面はその後に戻る。
Worker を起動できない環境では主スレッドへフォールバックする。
原寸 RAW 処理・高負荷な効果を含む全操作を Lightroom と同等の速度にしたわけではない。
コミット・公開・デプロイは行っていない。

## 2026-09-25 更新: フレーム単位の送信と描画経路の同期待ち削除（#233）

16ms のタイマーはフレーム間隔（16.7ms）より短く、速いドラッグでは変化したフレームの
約半分を捨て、空いている時も要求を 16ms 遅らせていた。次のように変更した。

- **送信（`app/coreReprocessDispatcher.js`）。** プレビュー要求は、変換中でなく、
  このフレームでまだ送っていなければ、同じタスクの終わり（マイクロタスク）に送る。
  呼び出し側が予約後に書いた状態も含まれる。変換中は既存の最新優先の枠に置き、
  `finally` が送る。同じフレーム（`document.timeline.currentTime`）で送信済みなら
  次の rAF まで待つ（非表示時は `setTimeout(0)`、rAF が止まる窓向けに 50ms の予備）。
  原寸要求は従来どおり 70ms。`clearCoreReprocessTimer()` がどの待機も取り消し、
  `coreReprocessTimer` は待機中は真のまま（書き出し前の flush と写真セッションの
  完了判定がこれを見る）。
- **確定時の重複変換をなくす。** `change` や数値欄の Enter/blur が、入力で既に要求した
  値を繰り返す場合は `onInput` を呼ばない。SilverCore のスライダーは
  {キー, 値, トークン} が一致すれば `onCommit` でも要求しない。除塵・修復が有効な時に
  最終値の原寸変換を捨ててやり直すことがなくなり、除塵検出はその一回の後に続く。
  変換が失敗した時は記録を消し、確定時に再試行する。
- **次のプレビューを先に送る。** 結果が届いた時に同じ世代・同じ画像の非原寸要求が
  待っていて、表示用プレビューの寸法が変わっていなければ、結果の適用・描画の前に
  次の要求を Worker に送る。フライトは各自のトークンで管理し、古い `finally` が新しい
  フライトの印を消さない。原寸要求は常に `finally` から送る。
- **WebGL 描画。** 上下反転を頂点シェーダーで行い、`UNPACK_FLIP_Y_WEBGL` による
  主スレッドの反転コピーをなくした（フレームバッファの向きは不変）。テクスチャは
  寸法が変わる時だけ `texImage2D` で確保してその直後に一度だけ `getError` を確認し、
  同寸は `texSubImage2D`。描画ごとの `getError` は削除（`?debugGL` で復活）。
  `#canvasContainer` の寸法は ResizeObserver で保持し（ResizeObserver のない環境だけ
  ウィンドウの `resize` で実測）、`adjustCanvasDisplay` は入力（原寸基準の寸法・容器・
  ズーム・DPR）が変わらなければ何もしない。容器の寸法が変わっても描画バッファは
  テクスチャに従うため、表示枠を合わせ直すだけで描き直さない（#261）。DPR 変更は
  `matchMedia` で検出する。
- **ズームは合成のみ。** ズームの各段は CSS 変換だけを変え、再描画しない。描画バッファは
  ズームではなく描画するテクスチャの寸法に従うため、100ms 後に表示用プレビューが
  新しい寸法で届いた時だけ変わり、同じタスクで描き直す。リサイズでバッファが消えて
  黒くなる問題（監査バックログ）もこれで解消した。

- **操作中の 16bit 面は Worker に残す。** 表示用プレビューが原画像と別の時だけ、
  操作中のフレームは 8bit 面と直方図用標本（最大 24,576 画素、16bit 付き）だけを送り、
  16bit 面は Worker が保持して次のフレームの作業バッファに再利用する。指を離した時、
  150ms 新しい要求がない時、書き出し前の flush、写真の切り替え、スナップショットの
  取得時に main が確定を送り、面を受け取る。指を離した時（数値入力、トラックの
  クリック、矢印キー、GPU 描画後の確定フレームを含む）に面を残すフレームがまだ
  変換中か待機中なら、確定の要求はそのフレームを待ち、届いた時点で送る。続けて
  ドラッグの入力が来れば要求は取り消し、150ms の待機が面を戻す（#229 レビュー
  R1-024）。確定までは `coreReprocessBusy()` が真。
  設定に残る測定（灰色点のクリック、期限切れ救済の解析＝ワンクリック色補正・救済の
  有効化・再解析・測り直しを伴う色のリセット）は `settleMeasurementInputs` で確定を
  待ち、16bit 面で測る（待つ間 Studio はビジー。裁切後の撮影窓検出も同じ関門で待つ）。
  8bit 標本で測ると保存される WB・解析値と書き出しが 1703835 と変わるため。
  面が失われていた（再利用済み・Worker 再起動）場合はそのフレームを面付きで変換し直す。
  プレビューが原画像そのものの時（16bit 書き出しの元）は常に両方の面を送る。
  `?retain16=0` で無効化できる。

検証: `coreReprocessDispatcher.test.mjs` が main.js の実関数で、空き時の同タスク送信、
変換中の最新優先、1 フレーム 1 送信、先行送信の受け渡し、待機の取り消し・flush・
完了判定、確定一回につき変換一回、16bit 面の保持と各契機での確定・失われた面の
再変換を確認する。`measurementBarriers.test.mjs` は保持中のフレームで灰色点・色補正・
再解析・色のリセットが確定を待って 16bit 面を測ることを確認する。
`conversionWorker.test.mjs` はカラー・白黒・正像で、確定した面と
直方図標本が非操作時の変換と完全一致し、2 フレーム目以降に画像サイズの 16bit 面を
確保しないことを確認する。Chrome smoke は
`realtime-preview-smoke.mjs` に信頼済みマウスのドラッグ（構造のみ、フレームレートの
閾値なし）と `texSubImage2D`・`getError` の計数を追加し、新しい
`webgl-preview-smoke.mjs` が向き（GPU と CPU の一致）、ズーム中の無描画（GPU・CPU・
枠プレビュー）、リサイズ・DPR 変更・コンテキスト喪失と復帰を確認する。
実機のフレームレート・遅延は #230 の計測基盤で別途測る。


## 2026-09-25 更新: 操作中だけ表示解像度を下げる段階（#263）

表示用画像は表示領域・DPR・ズームだけで決まり（最大 400 万画素）、1 フレームの
描画費用を見ていなかった。Linux の旧 AppImage（`WEBKIT_DISABLE_DMABUF_RENDERER=1`）
のように WebKitGTK がページをソフトウェアで合成する環境では、描画のたびに WebGL
キャンバスを CPU へ読み戻して合成するため、ドラッグ中は最大 4 MP を毎フレーム払う。

- **段階（`app/previewTier.js`）。** `previewTier` は `'normal'` と `'reduced'`。
  `'reduced'` はスライダーまたはトーンカーブのドラッグ（セッション）の中だけで、
  `getDisplayPreviewSize` の上限を 100 万画素にする。SilverCore の変換用プレビュー、
  各結果から作る表示用・WebGL 用の画像がこれに従い、`resizeWebGLCanvas` は描画
  バッファ（#233 以降はテクスチャの寸法）をこの上限で抑える。確定した表示は常に
  通常の段階から来る。
- **セッション。** 操作パネル内の `input[type=range]` への `pointerdown`（捕捉段階、
  拡大機ヘッドのように単独で配線された range も含む）で始まり、最初の
  `pointerup`・`pointercancel`（window の捕捉段階）または `change`（パネルの捕捉段階、
  スライダー自身の `change` より前）で終わる。カーブは `mousedown`/`pointerdown` から
  `mouseup`・`mouseleave`・`pointerup`・`pointercancel` まで。ズームは #233 以降
  合成だけなので対象外、パンも再描画しないので対象外。入力が 1 秒ない
  セッションは自動で終わる（終了イベントの取りこぼし対策）。
- **フレーム計測。** セッション中は rAF を一つ回す（非表示時は数えない）。最初の間隔は
  捨て、10 間隔以上の直近 30 間隔の中央値が 24ms かつ待機時の rAF 間隔の 1.3 倍を
  超えたら、そのセッションの終わりまで `'reduced'`。待機時の間隔は読み込み後と表示
  状態の変化ごとに測る（30Hz に制限された rAF を遅いと誤認しない）。M1 Pro では
  カーブが 60fps、SilverCore スライダーも主スレッドは空いているため発動しない。
- **最初から下げる場合。** `app/renderEnvironment.js` の `startsReduced` が真
  （Rust が報告した実効環境変数で DMABUF 無効・合成無効、または WebGL の
  レンダラー名が llvmpipe・softpipe・SwiftShader・Microsoft Basic Render Driver 等）
  なら全セッションが `'reduced'` で始まる。レンダラー名が伏せられている・空の時は
  ハードウェア扱い。それ以外の環境でも 2 セッション続けて下がったら以降は下げて始め、
  10 回目ごとに通常で測り直す。
- **入る時。** その場で `renderWebGL()`（寸法変更と描画を同じタスクで行い、消えた
  フレームを見せない）。SilverCore は次の tick で 1 MP の表示対象（#248: 寸法と
  保持レベルだけ。プレビュー Worker がレベルから作る）に切り替え、通常のものは
  保持する。主スレッドでは何も縮小しないため、空き時間の事前作成はなくなった。
- **出る時。** `'normal'` に戻し、保持したプレビューの寸法が今も合えば戻して
  `scheduleDisplayPreviewResize()` と `renderWebGL()`。縮小して変換したフレームが
  表示中なら、最終設定で通常寸法の tick を一回だけ要求する（寸法が一致して
  `scheduleDisplayPreviewResize` が何もしない時も。60 MP では原寸描画が走らず、
  縮小テクスチャが残り続けるため）。縮小フレームがまだ変換中の時（トラックの
  クリック、Worker が遅い時の指離し。フレームは終了後に届く）も同じ: プレビューの
  変換は縮小した対象かどうかを覚えており、この tick がそれを置き換え、届いた時点で
  送られる。その後ろに待っていた tick はこれに置き換わるので変換は増えない
  （#229 review R1-119）。この tick は live な設定を変換するので、
  スライダー自身の確定（#233 の重複排除）は追加の変換をしない。修復が有効でも
  各入力は（縮小した）プレビューを変換し、原寸面は修復のアイドル処理を待つ（#237）。
  現在の画素の原寸フレームが表示中（セッション中に届いた場合）なら、表示用の
  縮小コピーを作り直すだけで変換しない。セッション中に届いた同寸の原寸結果
  （修復処理、マスクの消去）は、どちらの段階のフレームが表示中でも通常段階の
  寸法でプレビュー Worker（16 MP 超は行帯）が作り直し、それが届くまで今の表示を
  残す。主スレッドで原寸全体を縮小しない（#229 review R1-123）。
- **確定状態の保護。** 縮小段階で作った表示画像はすべて記録する。表示対象
  （#248）は (レベル, 寸法) ごとに一つの物だが、縮小段階のものは段階ごとに別の
  物にする。後の窓で通常段階の寸法が同じになっても、その印（未確定）を引き継が
  ない（#229 review R1-089、R1-122）。保持した通常のプレビューがすでに縮小段階の
  寸法なら、段階は何も変えず、終了時の変換もない。
  `rememberPhotoSession` はセッション中・縮小フレームの表示中を未確定とし、
  `captureSnapshot` は保持した通常段階の `conversionPreviewImageData` を保存する。
  写真の切り替えはセッションを閉じるが、古い写真を再変換しない。フィルムストリップの
  タイルは通常寸法の tick を待ってから作る。
- **修復済みの表示用ソース（#237）。** 縮小段階の対象は自分では修復しない。
  通常段階の修復済みソースを水準とする縮小段階の表示対象を変換し、プレビュー
  Worker がそれを縮小段階の寸法へ再標本化する。最初の tick から塵は戻らず、新しい
  除塵要求もない。修復済みソースの作成は、セッション中に修復が確定した時も入力が
  300ms 止まった時も、保持した通常段階のプレビューに対して行う。縮小段階の対象の
  ために通常のものを捨てないので、終了時の通常寸法の tick もそれを変換し、
  アイドル時の原寸変換は修復済みの表示を保つ（#229 review R1-120）。
- **診断。** `?debug=1` のウィジェットにレンダラー・合成の判断・WebKitGTK の版・
  開始段階と、直前のセッションの段階・発動理由・p50/p95・描画バッファの寸法を出す。
  デスクトップでは最初の WebGL コンテキストの後に同じ内容を `log_webview_diagnostics`
  で端末ログ（`[webview]`）へ一行送り、`NEGATIVE_CONVERTER_FRAME_LOG=1` なら
  セッションごとの要約も送る。`<html data-preview-tier>` と
  `data-preview-tier-last-session` に現在と直前の段階を出す。
- **テスト用フック。** `?previewTier=reduced` は全セッションを縮小で始め、
  `?previewTier=normal` は常に通常のまま。

1 MP の上限と 24ms は Linux 実機で調整する定数。DPR 1・画面合わせの 1920×1080 窓では
表示が約 0.9 MP なので、この段階は何も減らさない（必要なら 0.5 MP を先に試す）。
M1 Pro で 16bit の 1809×1202 から 1224×816 を作る時間は約 33ms（Node、中央値）。

検証: `previewTier.test.mjs`（寸法・統計・発動条件・監視・記憶と再測定）、
`renderEnvironment.test.mjs`（レンダラー名の分類、`startsReduced`）、
`previewTierWiring.test.mjs`（main.js の実関数で、縮小中は 1 MP 以下、終了後の確定表示が
通常経路とバイト単位で一致、確定一回で変換は一回、履歴は通常段階、写真切り替えで
古い写真を変換しない、通常段階の寸法は従来と同一。縮小 tick の返事より先に離すと
変換は [1224×816, 1860×1240] で確定は通常経路と同一、同じ寸法の通常段階の表示対象は
未確定にならない、セッション中に届いた原寸結果で主スレッドの縮小は 0 回。修復済みの
表示用ソースも実関数で: 縮小 tick はどれも通常段階の修復済みソースを縮小段階の寸法で
変換し、300ms 止めても通常のものが残って縮小段階の対象は修復されず、終了時の tick は
通常の修復済みソースを変換する。セッション中に確定した修復と、窓の寸法が変わった後の
停止も、通常段階のプレビューを修復する）。Chrome smoke の

## 2026-09-25 更新: 原寸の拡大表示と表示用画像の Worker 化（#248）

拡大しても表示用画像（最大 4 MP）を CSS で拡大するだけで、原寸の細部は見えず、
ズーム・リサイズ・DPR 変更のたびに主スレッドが 16bit の全画素から表示用画像を
作り直していた（60 MP で 80〜155ms の長いタスク）。

- **本当の 1:1（第 1 部）。** `1:1` ボタンは画面合わせと等倍（1 画素が 1 デバイス
  画素、`max(1, 1 / (fit × DPR))`、ビュー中央）を切り替える。キー `1` も同じ、`0` は
  画面合わせ、ダブルクリックは従来どおり 2 倍。最大倍率は `max(8, 2 × 等倍)` で、
  どの DPR・窓でも原寸の 200 % に届く。表示は画像基準の百分率（100 % が等倍）。
  利用者による画面合わせへの復帰は表示サイズの確定を予約し、確定は予約時の変換元を
  記録して、写真の切替・回転・切り抜きの後には何もしない。
- **正確で速いカーネル（第 2 部）。** `resizeDisplayPreview` は列・行ごとの表を使い、
  演算の式と順序を変えずに両方の面を 1703835 とバイト単位で同一に保つ（Node で
  約 2 倍）。入力中の再標本化は削除した: tick は現在の表示対象を変換し、ResizeObserver
  と DPR の `matchMedia` が呼ぶ確定フック（`refreshDisplayPreviewForViewport`）が
  対象の寸法を動かす。現在の寸法が新しい寸法より 15 % 以内大きいか約 5 % 以内小さい
  間は何もしない（ヒステリシス、調整用の推定値）。
- **保持レベルと Worker での最終縮小（第 3 部）。** `processNegative` は変換元ごとに
  一度だけ、k × k の箱平均（`k = max(1, floor(min(W / capW, H / capH)))`、4 MP の上限を
  下回らない。60 MP で k 3・3178×2112・54 MB、24 MP で k 2、それ以下は変換元そのもの）
  を幾何 Worker の帯（回転・切り抜きあり）か主スレッドの約 12ms の行帯で作り、
  `state.displayLevelImageData` に置く（履歴の参照キー）。
  `conversionPreviewImageData` は画素を持たない表示対象（寸法とレベル、寸法ごとに
  同一のオブジェクト）で、「別のプレビューか」は同一性でなく寸法で決める。
  プレビュー要求はレベルを一度だけ送り、以後は寸法だけ（`display`）。Worker は
  レベルを変換元の幾何のまま縮小し（レベルに対して 2 倍までは双線形、それ以上は
  正確な面積平均）、寸法ごとに保持して変換する。GPU プレビューの `prepare`・
  修復済みプレビュー・テストストリップも同じ表示対象から作る。#242 の比較表示は
  表示対象の最初の押下でレベルから同じ縮小を主スレッドで一度だけ行い（16bit を
  Worker と同じく 8bit に丸める）、同じ表示対象の間は保持する。
- **自動 WB の標本（フラグ付きの変更）。** 自動グレーポイントは、`processNegative` の
  最初のフレームと一緒に Worker がレベルを長辺 1024 px に縮小して変換した正像から
  推定する（意味アンカーの推定も同じ標本。期限切れフィルム救済中の写真の意味マップは
  救済の測定に重みを与えるので、1703835 と同じく画面のフレームから推定する）。
  窓の大きさ・DPR・ズームで推定値が変わらなくなった。利用者が決めた WB は変わらない。
  サンプル点がなく利用者 WB もない自動推定のカラー写真は、推定値が一度だけ変わり得る。
- **期限切れフィルム救済の測定（フラグ付きの変更、#229 review R1-085）。** 表示より
  大きい写真では、変換直後の最初のフレーム（読み込み・写真を開く・切り抜き）で取る
  救済の測定（救済中の意味マップと、それが重みを与える測定も同じフレーム）が、
  1703835 の変換元の 2×2 双線形縮小ではなく、表示レベル（k × k の箱平均の後に
  双線形または面積平均の縮小）から作ったフレームを読む。保存される測定（レベル、
  色の表、かぶりの面、それが決める明るさとコントラスト）がわずかに動き得て、救済した
  写真の書き出しもそれに従う（全フィルム種）。1703835 と同じく表示サイズのフレーム
  なので、窓の大きさと DPR に従う。表示に収まる写真は変わらない。
- **原寸の結果は表示用画像と一緒に届く（第 4 部）。** 原寸変換の要求は要求時の
  通常段階の表示寸法（`displayTarget`）を持ち、Worker が同じ表示フィルターで両方の
  面と直方図用標本を作って転送する。main は寸法を確かめてアップロードするだけで、
  寸法が変わっていれば一旦そのまま表示して確定フックが作り直す。現在の原寸画像の
  表示サイズ変更は、16 MP 以下はプレビュー Worker（保持しない）、それ以上は主
  スレッドで約 12ms の行帯（正確なカーネル）で作り、その間は古い表示を残す。検出など
  画像全体の修復結果も同様。ブラシ大の修復（除塵ストローク、AI 修復の結果）は
  表示フィルターの範囲だけを更新する（`updateDisplayPreviewRect` はフィルターの種類を
  見る）。コアスライダー後の確定待ちは 1200 + 600ms から 400 + 300ms に短縮した。
- **ズームに依らない基底と詳細レイヤー（第 5 部）。** `getDisplayPreviewSize` は
  ズーム 1 で計算する。基底の 1 テクセルが 1.25 デバイス画素を超えると、
  `canvasTransformWrapper` 内の第 2 のキャンバス（`#glDetailCanvas`、WebGL2、同じ
  Step-3 プログラム・ユニフォーム・カーブ）が、見えている範囲と 128 px の余白を
  最大で 1 原寸画素 = 1 デバイス画素の密度で表示する。変換前の CSS 矩形に置き、
  確定したパンはデバイス画素に揃える（揃えたパンで計画し直した領域が動かなくなるまで繰り返すので、写真に戻った時の同じビューはパンを保つ）。画素は、現在の原寸画像があればその切り抜き
  （修復を含む）、なければプレビュー Worker の `roi` メッセージ（変換元の行を
  転送、16 MP まで、半分以下の密度では Worker で箱平均。レベルで足りる時はレベルの
  切り抜き）。変換は固定寸法の `roi` スロットで、基底の解析（`channelData` と正像の
  解析をそのまま）と、その位置の覆い焼き・フラットフィールドを使う。解析標本が
  あれば書き出しと同じ画素になる。キャッシュ済みのレベルは置き換えない。
  スロットは空き時間に準備する。領域には変換元・再開の世代・設定のトークンを付け、
  より新しい設定の基底の上には描かない: ドラッグ中（GPU プレビューのフレームを含む）
  は隠れ、基底が落ち着いた後に変換し直す。切り抜き・比較・除塵マスク・覆い焼き・
  サンプリング・AI ブラシ・枠プレビューなどの CPU 表示・縮小段階・WebGL1 では
  出さない。`?detailLayer=0` で無効。

仕様との違い: 仕様はドラッグ中にも領域を毎 tick 変換し、基底を確定時に変換する案を
挙げていた。この版では、ドラッグの基底は #239 の GPU プレビュー（遅い環境では
#263 の縮小段階）が描き、Worker で変換する領域は毎フレームの GPU 描画に追いつけず
常に古くなるため、ドラッグ中は隠して確定後に戻す。任意項目（512² タイルの LRU、
領域用の第 2 Worker、原寸クライアントのリクエスト単位の入力キャッシュ）は入れて
いない。回転・切り抜きのある画像では、幾何 Worker（#244）が帯の描画と一緒に
その帯のレベル行を作り（帯の開始行を k の倍数に揃える。画素は変わらない）、
`processNegative` はレンズ補正で画像が変わらない限りそれを使う。幾何が恒等の画像
（復号した基底そのもの）は主スレッドの行帯で作る: 復号後の Worker（#232）は後で
切り抜かれるかを知らず、切り抜かれる RAW ごとに 54 MB と約 150ms を無駄にするため。
